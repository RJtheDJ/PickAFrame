# PickAFrame architecture

How the app is organised, and where new features plug in. Read this before
adding a screen or a backend. Who is building what, and what is finished,
is in [ROADMAP.md](ROADMAP.md).

## Layers (MVVM + repositories)

The app follows the MVVM structure from the proposal (section 3.2.2), plus a
**repository** layer for data access:

```
 views/  widgets/          what the user sees; no business logic
      │  listens to
 view_models/              screen state + actions (ChangeNotifier)
      │  uses
 models/  services/        pure data & maths  /  device features (camera, export, ...)
 rendering/                the frame visualizer engine (painters + GPU shader)
      │  reads & writes through
 repositories/             interfaces for stored data (auth, drafts, vendors, orders)
      ├─ in_memory/        stand-ins for tests and offline development
      └─ firebase/         Firebase Auth + Firestore implementations (in use)
```

Rules that keep the layers independent:

1. **Screens never import Firebase.** Only `lib/repositories/firebase/`,
   `lib/app/` and `lib/main.dart` may. Screens and view models depend on the
   interfaces in `lib/repositories/`, obtained with `AppScope.of(context)`.
2. **Models are plain Dart.** Each stored model has `toJson`/`fromJson` using
   plain maps, which is what Firestore stores. `FrameDesign` uses
   `encodeDesign`/`decodeDesign` in `lib/data/design_codec.dart`.
3. **Lengths are millimetres** everywhere in code and storage. Only the UI
   shows cm/m (`lib/models/units.dart`).
4. **Catalogue items are stored by id** (`'cherry'`, `'gold_leaf'`), never
   copied, so updating a texture updates every saved draft.

## Folder map

| Path | What lives there |
|---|---|
| `lib/main.dart` | Entry point: starts Firebase and picks the data sources (`AppDependencies.firebase()`). |
| `lib/firebase_options.dart` | Generated by `flutterfire configure`. Git-ignored; each developer generates their own. |
| `lib/app/` | App-wide wiring: `AppDependencies` + `AppScope`, and `app_theme.dart`. Routing goes here too. |
| `lib/models/` | Data and pure logic: `FrameDesign`, `MatSpec`, mat presets, perspective maths, units, `Draft`, `FramingOrder`, `Vendor`, `UserProfile`, `RoomScene`. |
| `lib/data/` | Built-in catalogues (finishes, mat colours, rooms) and the design codec. |
| `lib/rendering/` | The 2.5D frame engine: layout (mm → px), lighting, profile shading, CPU painters, GPU shader painter, room painter. |
| `lib/services/` | Device and file work: picking/cropping artwork, ML Kit scanner, textures, export. |
| `lib/repositories/` | Data-access interfaces, plus `in_memory/` and `firebase/` implementations. |
| `lib/view_models/` | One view model per screen. |
| `lib/views/` | Full screens (`welcome_screen`, `catalog/catalog_screen`, `editor_screen`, `artwork_crop_screen`). |
| `lib/widgets/` | Reusable pieces of screens, one folder per screen (`welcome/`, `catalog/`, `editor/`, `preview/`). |
| `shaders/` | `frame_material.frag`, the per-pixel lighting shader. |
| `assets/` | Wood/metal PBR textures, ornate moulding strips. |
| `cloudflare/artwork-worker/` | Cloudflare Worker that will store artwork images in R2 (in progress, see [plans/r2-exhibition.md](plans/r2-exhibition.md)). |
| `tools/` | `make_moulding_strip.py`: turns a moulding photo into a strip + normal map. |
| `backend/` | Optional Python helper (background removal); not used by the app. |
| `test/` | Unit and widget tests (`flutter test`). |

## The visualizer engine

- `FrameDesign` (mm) → `FrameLayout.fit` → screen rectangles.
- The moulding is drawn by `ShadedFramePainter` (GPU shader with normal and
  roughness maps, one light), falling back to `FramePainter` (CPU gradients)
  where shaders are unavailable.
- `MatPainter` draws bevels, the double-mat reveal and all cast shadows.
- `FrameRenderer` assembles frame, mat, artwork and wall. Its
  `RepaintBoundary` is what `renderPng` exports at 3000 px.
- `RoomPreview` places one framed piece in a drawn room (`RoomPainter`,
  `room_catalog.dart`).

## Firebase (in use)

- Packages: `firebase_core`, `firebase_auth`, `cloud_firestore`,
  `google_sign_in`. Each developer runs `flutterfire configure` to create
  their own `lib/firebase_options.dart` (git-ignored).
- `lib/repositories/firebase/` has `FirebaseAuthRepository`,
  `FirestoreDraftRepository`, `FirestoreVendorRepository` and
  `FirestoreOrderRepository`. Each `implements` the matching interface;
  `test/data_layer_test.dart` shows the contract.
- `main.dart` calls `Firebase.initializeApp` and runs the app with
  `AppDependencies.firebase()`. Tests use `AppDependencies.inMemory()`.
- Google sign-in is wired on the welcome screen
  (`widgets/welcome/quick_auth_section.dart`). Email sign-in screens are not
  built yet.

### Firestore collections

Documents are exactly the models' `toJson()` output.

| Collection | Document id | From | Key fields |
|---|---|---|---|
| `users` | auth uid | `UserProfile` | `role` (`artist` / `galleryOwner` / `frameShopOwner`), `vendorId` |
| `vendors` | auto | `Vendor` | `ownerUid`, `latitude`, `longitude`, `specialties` |
| `drafts` | auto | `Draft` | `ownerUid`, `design` (see codec), `status`, `artworkUrl`, `previewUrl`, `updatedAt` |
| `orders` | auto | `FramingOrder` | `customerUid`, `vendorId`, `specLines`, `stage`, `quoteRm` |

Suggested indexes: `drafts` on (`ownerUid`, `updatedAt` desc); `orders` on
(`customerUid`, `createdAt` desc) and (`vendorId`, `createdAt` desc).

Security rules outline: users read/write their own `users` doc and their own
`drafts`; anyone signed in reads `vendors`; only a vendor's owner writes it;
an order is readable by its customer and its vendor's owner, and only the
vendor's owner changes `stage`.

## Image storage: Cloudflare R2

The proposal named Firebase Storage; the team has switched to **Cloudflare
R2** for image files. Firestore still holds the draft metadata.

- The app never holds R2 credentials. It sends each PNG with the user's
  Firebase ID token to the Worker in `cloudflare/artwork-worker/`, which
  verifies the token and writes to a private bucket.
- Each draft has one object, the cropped artwork, at
  `drafts/{uid}/{draftId}/artwork.png`. `Draft.artworkUrl` stores the Worker
  path, not a public URL. The framed look is drawn on the device from the
  artwork plus `Draft.design`, so no preview image is stored
  (`Draft.previewUrl` is unused).
- Full design, API and task list: [plans/r2-exhibition.md](plans/r2-exhibition.md).

## Google Maps (not started)

- `google_maps_flutter` for the workshop directory map; a places
  autocomplete package for the vendor address picker during onboarding.
- The API key goes in `android/app/src/main/AndroidManifest.xml` (a
  `com.google.android.geo.API_KEY` meta-data entry) and `ios/Runner/AppDelegate.swift`.
  **Restrict it** to the app's package name/bundle id in Google Cloud and keep
  it out of public repos.
- Workshop data comes from `VendorRepository.watchVendors()`; the map only
  displays `Vendor.latitude/longitude`.
- The catalogue screen has a `WorkshopMapPlaceholder` card to swap for the
  real map.

Profile) for artists and gallery owners; frame shop owners land on a vendor

Orders; settle on one set of tabs when the app shell is built.
